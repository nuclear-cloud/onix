# Архітектурний Дизайн Проекту (Project Architecture Design)

Цей документ описує цільову архітектуру системи стандартизації книг, яку ми проектуємо разом.

## 1. Загальна Концепція (High-Level Concept)

Система працює як "конвеєр" (Pipeline):
`Сирі Дані (JSONL)` -> `[ETL Процес]` -> `Стандартизовані Дані (ONIX)` -> `База Даних`

Ми використовуємо підхід **Clean Architecture** (Чиста Архітектура), щоб розділити код на незалежні шари. Це дозволяє легко змінювати одну частину системи, не ламаючи інші.

## 2. Шари Архітектури (Layers)

### Шар 1: Домен (Domain Layer) 🧠
*Серце системи. Тут живуть "правила гри".*
- **Що тут є:** Тільки визначення типів даних (Models).
- **Приклад:** Ми кажемо системі: "Книга ОБОВ'ЯЗКОВО повинна мати назву (title) і ISBN".
- **Файли:** `app/domain/onix.py`, `app/domain/yakaboo.py`
- **Залежності:** Ні від чого не залежить. Найстабільніша частина.

### Шар 2: Аплікація / Сервіси (Application Layer) ⚙️
*Робочі конячки. Тут відбувається магія.*
- **Що тут є:** Логіка трансформації, перевірки, обробки.
- **Приклад:** "Візьми сирі дані з Yakaboo, перевір їх через Доменні правила, і перетвори в ONIX".
- **Файли:** `app/services/pipeline.py`, `app/scraper/yakaboo/transformer_v2.py`
- **Залежності:** Залежить від Домену.

### Шар 3: Інфраструктура (Infrastructure Layer) 🔌
*Зв'язок із зовнішнім світом.*
- **Що тут є:** Робота з файлами, базами даних, мережею.
- **Приклад:** "Прочитай файл з диска", "Збережи в Postgres".
- **Файли:** `app/core/database.py` (планується), логіка читання файлів у `pipeline.py`.
- **Залежності:** Залежить від Аплікації.

### Шар 4: Інтерфейс (Presentation Layer) 🖥️
*Як людина взаємодіє з системою.*
- **Що тут є:** CLI команди (термінал), API (якщо буде).
- **Приклад:** Коли ви пишете `python manage.py standardize ...`
- **Файли:** `manage.py`
- **Залежності:** Залежить від Аплікації.

## 4. Ключові Рішення (Key Decisions)

1.  **Pydantic для Валідації:** Ми відмовилися від ручної перевірки типів (`if type(x) == int`) на користь декларативних моделей. Це зменшує кількість помилок на 90%.
2.  **Streaming (Потокова обробка):** Ми не завантажуємо весь файл (9GB) в пам'ять. Ми читаємо його по одному рядку. Це дозволяє працювати навіть на слабких серверах.
3.  **Modular Transformers:** Кожен магазин (Yakaboo, Vivat) має свій власний "перекладач" (Transformer), який підключається до загального Пайплайну. Якщо треба додати новий магазин, ми просто пишемо новий файл трансформера, не чіпаючи основний код.

## 5. План Розвитку (Roadmap)

- [x] **Етап 1: Фундамент.** Створення Доменних моделей та базового Пайплайну. (Виконано)
- [ ] **Етап 2: База Даних.** Підключення PostgreSQL для збереження результатів, а не тільки у файл.
- [ ] **Етап 3: API.** Створення веб-сервісу (FastAPI), щоб можна було звертатися до системи через HTTP, а не тільки через консоль.
- [ ] **Етап 4: Моніторинг.** Додавання логування помилок у Sentry або Prometheus.
